# 0.4.0 전면 감사 후속 수정 — 2026-10-09

사용자가 전면 감사의 **출시 전 수정 권고 9건과 낮은 우선순위 2건 전체**의 원인 수정과 점수 재확인을
요청했다. 이 문서는 수정 전 감사와 구분되는 후속 기록이다. 작업 기준은 통합 PR #291의 `fc588ec`이며,
6113에 배포된 런타임 `1e86796`과는 구분한다. `orchestrate`에 따라 자식 에이전트 두 명만 사용했다
(Astra High: 데이터 보존, Sol High: 설정·업로드). 리드가 Recall·성능을 구현하고 전체 변경을 검토했다.
외부 reviewer CLI나 생성형 모델 호출은 사용하지 않았다.

**고위험:** 원본 PostgreSQL 데이터 보존, 작업 claim 소유권, canon 파생 기억의 완전한 재구축,
Recall 후보 선택과 provenance. 마이그레이션·프롬프트·추출 세대·provider payload·기본 packet 정책은 바꾸지 않았다.

## 정규화와 generation

이 변경은 `clean-v3`의 출력 규칙을 바꾸지 않는 탐색 알고리즘 최적화다. 기존 정규식과 6,000개 결정적
합성 입력, 별도 검토의 Unicode 역참조 9,024개를 비교했으며 차이는 없었다. Python IGNORECASE의
태그 이름 인식과 backreference의 단순 소문자 비교가 다르므로 dotless i·long s를 임의로 ASCII에
합치지 않는다. 원문은 수정하지 않으며 API 저장 후 DB에서 원문·정규화 결과를 재조회했다.
출력 의미·projection 입력이 같으므로 generation을 바꾸거나 기존 행을 덮어쓰지 않았다(D20/D21).

## 성능 재현

동일 머신, 격리 PostgreSQL 55439, 실제 reconcile → bodies → DB 재조회. 수정 전·후 각 3회,
원문 동일·HTTP 200·정규화 `x`를 모두 확인했다. 전체 suite와 replay도 같은 머신에서 실행 중이므로
아래 수치를 일반적인 사용자 지연이나 정밀 성능 게이트로 확대하지 않는다.

| 합성 입력 | 수정 전 API ms (3회) | 수정 후 API ms (3회) |
|---|---|---|
| 미완결 `<think>` 반복, 70,001자 | 2066.08 / 2164.31 / 2063.03 | 30.01 / 19.29 / 21.51 |
| 닫힌 태그 대조군, 160,001자 | 19.28 / 21.29 / 20.46 | 52.36 / 33.47 / 33.53 |

느린 로컬 HTTP는 40ms마다 4bytes를 전송했다. 기존 100ms inactivity 설정은 thread를 약
497–499ms 유지했다. 수정 후 100ms HTTP 기한에서 thread 종료는 101.82 / 101.48 / 101.28ms,
호출자의 50ms 대기는 50.11 / 50.10 / 50.08ms였다. 모든 synthetic server와 thread를 정리했다.

**기한의 한계:** 네트워크 없는 resolver stub에서는 150ms 기한을 넘겨 392ms에도 thread가 살아 있었다.
`asyncio.run`이 OS resolver 종료를 기다리기 때문이다. 슬롯은 종료까지 유지되어 동시 호출·정리가
8개를 넘지 않는다. 따라서 모든 thread가 2배 기한 안에 종료한다는 주장은 하지 않는다.
