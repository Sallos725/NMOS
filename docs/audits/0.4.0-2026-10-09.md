## 확인한 네 결함과 보장

### 1. 최종 upload chunk의 응답 유실 후 재시도

**보장:** 동일한 upload의 검증된 이전 chunk 재시도는 데이터를 중복 기록하지 않으며,
검사나 복원 시작 이후에는 upload를 변경할 수 없어야 한다.

기준 후보는 마지막 chunk 기록 후 state가 `received`가 되므로 동일 index/hash의 재시도도 409로 거부했다.
panel의 응답 유실 재시도 경로와 연결된 결함이다.
수정은 `receiving` 또는 `received`에서 hash를 검증한 뒤 이전 index와 hash가 모두 같은 경우에만 그대로 응답한다.
새 chunk는 `receiving`에서만 허용하며 `checking/checked/restoring/restored/refused/failed`의 재시도는 거부한다.
인증, archive 검사, 복원 lock 또는 스키마를 바꾸지 않았다.

`test_panel_restore.py`는 최종 chunk 동일 재시도, 다른 내용·다음 index 거부와 spool bytes 불변을 확인한다.
plugin `restore.test.ts`는 최종 응답 유실 후 같은 body를 보내고 실제 기록이 한 번인 경로를 확인한다.
DB 없는 upload 거부/재시도 검사 9건과 plugin 전체 222건은 통과했다.
실제 host proxy의 응답 유실 사례를 새로 실행한 것은 아니다.

### 2. normalize 완료 뒤 중단된 restore의 상태 복구

**보장:** immutable source는 보존하며 derived state는 재시작 뒤 복구할 수 있어야 한다.
기존 대화와 그 관측을 복원 때문에 잃지 않아야 한다.

전용 PostgreSQL에서 실제 archive를 만든 뒤 기존 Gold=10 대화가 있는 target에 복원했다.
`normtext.backfill` commit 다음 `sync_rules` 직전에 실패를 주입하자 normalized text 누락은 0이지만 복원 대화의 history는 비었다.
기준 후보는 성공한 다음 startup과 noop sync 뒤에도 Gold=100을 복구하지 못했다.
worker가 먼저 text를 채우는 경로도 있으므로 text 누락만 복구 신호로 쓰는 방법은 충분하지 않다.

수정된 `sync_rules`는 current-rule observation이 없는 message revision을 normalized text와 독립적으로 찾는다.
UUID keyset으로 최대 500건씩 방문하며 기존 positive observation을 보존하고 내부 commit을 추가하지 않는다.
따라서 설정의 rule 변경 transaction 경계도 유지한다.
500건 제한은 fetch 크기이며 state transaction의 commit 단위나 durable checkpoint가 아니다.
state transaction 안에서 중단되면 다음 startup에서 그 scan을 재시도한다.
일치하지 않는 message는 완료 표지가 없으므로 startup마다 한 번 다시 읽는다. 새 schema 없이 선택한 비용이며 아래 synthetic 측정으로 구분한다.

lead가 동일 재현기를 고정된 수정 스냅샷에서 전용 55439 DB로 실행한 결과(exit 0):
실패 주입 뒤 `missing_text=0, history={}`였던 대화가 재시작과 noop sync 뒤 Gold=100으로 복구되고,
기존 대화 Gold=10은 유지됐다.
원본 로그는 `lead-fixed-recovery.log`; 사용한 고유 DB
`nmos_test_independent_66b0a972e4`, `nmos_test_independent_14127eaf7b`는 정리됐다.

회귀 테스트 `test_panel_restore_recovers_card_state_in_an_existing_install`은 즉시 복원과 중단 후 재시작,
card-bound 관측, 기존 observation ID 보존, source content/hash 불변을 검사한다.
`test_missing_state_scan_crosses_no_match_batches_once`는 두 batch 이상 무일치 row를 방문하고 종료하는 경로를 검사한다.

### 3. 비활성 reply가 supportive memory를 계속 깨우는 현상

**보장:** 비활성 소스는 다음 packet에 영향을 주지 않으며 historical replay는 그 시점의 증거를 사용해야 한다.

기준 후보에서 disabled reply의 문장만 echo에서 비-echo로 바꾸자 packet의 identity 배치가 True에서 False로 달라졌다.
disabled reply가 supportive memory rest 판정에 참여한 것이 실제 synthetic 재현으로 확인됐다.
수정은 live membership의 eligible turn만 읽고, replay에는 재구성된 as-of membership과 immutable revision metadata의
disabled/comment/`allBefore` cut을 사용한다. 현재 lifecycle이나 현재 turn을 historical 판단에 사용하지 않는다.

lead의 수정 스냅샷 재현(exit 0)은 disabled echo와 같은 disabled non-echo 모두
`tired=[('fact', '1')], rested=1, placed_identity=False`를 반환했다.
원본 로그는 `lead-fixed-inactive-echo.log`; 고유 DB `nmos_test_independent_8bc1634b69`는 정리됐다.
`test_reply_echo_uses_eligible_sources_and_the_metadata_as_of_replay`는 disabled, comment, pre-cut 제외와 active echo 유지,
나중의 metadata 변경·edit·undo·reorder가 과거 판단을 바꾸지 않는 것을 검사한다.

이 증거는 invariant 7의 synthetic 정확성 검사다.
recall semantic 보정에 필요한 기존 gate DB zero-call replay와 reduced live run의 새 수용 결과는 아직 없으며,
과거 Phase 34 live 결과를 이번 보정의 통과 근거로 재사용하지 않는다.

### 4. 임시 PostgreSQL 종료 확인 없이 복사본 승격·삭제 진행

**보장:** 임시 cluster가 동작할 수 있는 동안 원본을 retire하거나 copy를 promote/delete하지 않아야 한다.

기준 후보는 copy 검사 시작을 try 바깥에서 수행하고 stop 결과를 무시했다.
오류 때 staging을 지우며 다음 시도도 기존 staging을 무조건 지웠다.
확인된 fault reproduction에 따라 attempted start를 teardown 범위에 포함하고,
`pg_ctl status`가 stopped(return 3)를 보고한 경우에만 promotion 또는 cleanup을 허용한다.

종료를 확인하지 못하거나 stop 오류/중단이면 원본과 staging을 유지하며 actionable error로 멈춘다.
다음 adoption도 기존 staging의 종료를 먼저 확인한다.
경로 ACL, 인증, data folder 기본값은 바꾸지 않았다.
`test_native_launcher.py`에는 start 실패, check 실패, stop 실패, status 0/1/4,
staging 재시도와 OS error/KeyboardInterrupt에서 promotion·retirement·삭제가 없는 회귀 검사를 추가했다.
실제 OS process 실패 조건 전체의 복구를 실행했다고 주장하지 않는다. 현재 target build/smoke와 device 증거는 별도다.
